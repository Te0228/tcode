# Memory 设计

> **这是解释性文档,不是决策来源。** 权威决策在 [spec.md](../spec.md) §5.7 / §9;这份文档解释"为什么这么设计、怎么串起来的",方便读代码时对照。两边冲突时以 spec.md 为准,并且应该回头修这份文档。

---

## 1. 一句话概括

记忆是**分层的静态 Markdown 文件**,启动时读进 system prompt,agent 也能通过 `remember` 工具往里写。没有向量库、没有语义检索、没有后台自动总结。

## 2. 为什么需要它

没有记忆时,每个新 session 都从零开始:你上次告诉 agent "这个项目用 pnpm 不用 npm",下次它照样敲 `npm install`。

而 context 管理(spec §3.1)解决不了这个问题——两者的时间尺度根本不同:

| | 生命周期 | 存在哪 | 解决什么 |
|---|---|---|---|
| **Context 管理** | 单个 session 内 | `session.messages` + `compactions` | 一轮对话太长,装不进 context 窗口 |
| **Memory** | 跨 session,长期 | `AGENTS.md` 文件 | 下次启动时还知道这个项目的约定 |

Context 管理是**压缩**,memory 是**沉淀**。compaction 的摘要会随 session 一起被遗忘;memory 不会。

## 3. 两层结构

```
~/.tcode/AGENTS.md          用户级 —— 跨项目的个人偏好
                            "回答用中文" / "提交信息写中文" / 常用工具链

<project>/AGENTS.md         项目级 —— 这个代码库的约定
  (回退 TCODE.md)           "测试用 vitest" / "改代码前先读 spec.md"
```

### 为什么是两层而不是一层

一层放不下两种性质完全不同的东西:

- "回答用中文" 是**跟着人走**的,换到任何项目都成立。放进项目的 `AGENTS.md` 里,别的项目就享受不到,而且提交上去会污染仓库(那是你的个人偏好,不是团队约定)。
- "测试用 vitest" 是**跟着代码库走**的,换个人来也成立,而且**应该**提交进仓库让所有人共享。

### 加载顺序与优先级

**两层都加载,不是二选一。** 拼进 system prompt 时:

```
用户级在前  →  项目级在后
```

顺序是有意的:**更具体的层放在后面**。一方面 prompt 里靠后的内容权重更高,另一方面 prompt 里会明确告诉模型"两层冲突时项目级优先"。

例:用户级写"回答用中文",项目级写"这个仓库的注释一律用英文"——不矛盾,各管各的。真冲突时(用户级"用 npm",项目级"用 pnpm"),项目级赢。

同一个项目目录下 `AGENTS.md` 和 `TCODE.md` 同时存在时,只取 `AGENTS.md`。

## 4. 写入:`remember` 工具

```jsonc
{ "scope": "user" | "project", "content": "string" }
```

**追加式,不是覆写。** 往对应文件末尾追加一条 `- xxx`,不会重写用户已有的内容——记忆文件是用户自己也会手写编辑的,agent 没有资格整篇替换它。

### 安全设计:为什么没有 `path` 参数

这是整个设计里最需要注意的一点。

spec §6 规定所有路径类工具都必须在 `ROOT` 内。但用户级记忆在 `~/.tcode/`,**在 `ROOT` 之外**——`remember(scope: "user")` 是这条规则的唯一例外。

之所以敢开这个例外,是因为**目标路径写死在代码里,模型完全无法影响**:

```
scope: "user"     →  ~/.tcode/AGENTS.md      (写死)
scope: "project"  →  <ROOT>/AGENTS.md        (写死)
```

工具的 input schema 里**没有 `path` 字段**。如果有,这个工具立刻变成一个"绕过目录检查写任意文件"的后门——模型可以 `remember({ path: "~/.ssh/authorized_keys", ... })`。

`tests/unit/remember.test.ts` 里有两条测试锁死这一点:一条断言 schema 的字段只有 `scope`/`content`,另一条真的塞一个 `path: "../../escape.md"` 进去,断言它被无视、文件没被创建。改这个工具时不要动这两条测试。

### 强制打印

每次写入都会在终端打印一行:

```
✎ remembered (project) → AGENTS.md: This project uses vitest, test command is npm test.
```

这是**强制的**,不是可选的日志。理由:记忆的影响跨越 session,用户必须始终知道 agent 记了什么——否则几周后 agent 的某个奇怪行为会变成无法追查的谜。

### 子 agent 的权限

| role | 能写记忆吗 |
|---|---|
| `general` | 能 |
| `explore` | **不能** |

`explore` 是只读调查角色(找"这个函数在哪些地方用到了"这类问题)。让一个搜索任务往记忆里沉淀"持久约定",既没道理也容易写进噪音。

## 5. 上限与截断

记忆是**全量**拼进 system prompt 的,所以它自己会占 context。没有上限的话,一个几千行的 `AGENTS.md` 能把 context 吃掉一大半。

上限是 `MEMORY_MAX_TOKENS`(默认 4000)。规则见 spec §9.4,三条:

**1. 层间:从用户级开始砍,项目级最后动。** 理由和优先级一致——项目级更具体、更可能和当前任务相关。

**2. 层内:按条目截断,不按字符。** 记忆文件是 `- xxx` 的列表,按字符切会切出半句话:

```
按字符切(旧):  - 部署前必          ← 残句,模型可能照着半句瞎猜
按条目切(现):  整条保留,或整条丢弃
```

一条被切成半句的记忆比没有这条更危险,所以条目是最小不可分割单位。文件开头的标题/说明段落不参与条目截断。

**3. 层内:保留最新的条目,丢弃最旧的。** `remember` 追加到末尾,所以越靠后越新;新记忆通常是对旧记忆的修正,冲突时应该新的赢。

丢弃时会在启动时**逐条列出**丢了什么,否则用户没法知道该清理哪些。

### 踩过的两个坑

**坑一:截断标记本身要占 token。** 第一版砍完用户级之后,总量因为多了个标记又超回上限,循环继续往下,把本该保住的**项目级**也砍成了空字符串——正好砍反。修法是给标记预留预算。

**坑二:小预算下标记会挤掉它要宣告的内容。** 改成按条目截断后又发现:标记写得太长时,预算全被标记吃掉,三条记忆一条都留不下,只剩一个孤零零的标记。修法是缩短标记 + 加保底规则(算上标记一条都放不下时,仍保留最新的那一条)。

这两个坑是同一类错误:**没把"元信息"自己的开销算进预算**。

## 6. 时机:什么时候读、什么时候截断

这一节单独拎出来,因为"读"和"写"的时机是**不对称**的,而这个不对称会产生反直觉的后果。

```
进程启动
  └─ loadMemory()  ←── 读取 + 截断,整个进程生命周期里只发生这一次
       └─ system prompt 拼好,此后固定不变

session 运行中
  └─ remember()  ──→  立即写盘,不做任何上限检查
                      当前 session 的 system prompt 不热更新
```

### 截断只发生在读取时,不发生在写入时

`appendMemory()` 里**没有任何大小检查**——它只管追加。上限 `MEMORY_MAX_TOKENS` 是 `loadMemory()` 读取时才施加的。

实测(`MEMORY_MAX_TOKENS=4000`):

```
连写 3 条 × 20000 字符  →  磁盘文件实际 60029 字符   (写入端不设限)
下次启动 loadMemory()   →  只有 16000 字符进 prompt  (truncated = true)
```

所以**磁盘上的文件和实际生效的内容会脱节**。文件可以长到几百 KB,但每次启动只有前 4000 tokens 真正影响模型行为,其余静默丢弃(只在启动时打一行 warning)。

### 后果一:当前 session 里刚记的东西不生效

system prompt 在启动时就拼好了。`remember` 写完文件之后:

- 文件已经落盘,**下次**启动生效
- **本次** session 里,模型只是通过 tool_result 知道"我刚调了 remember",记忆本身并没有以记忆的身份进入 prompt

对用户来说这通常无感(模型刚记的东西还在上下文里),但如果这轮 turn 之后触发了 compaction 把那段压掉了,模型就可能"忘记"自己刚记过——直到下次启动。

### 后果二:超限时丢的是最旧的条目(已定案,spec §9.4)

早期版本按字符截断且保留文件**开头**,而 `remember` 追加到**末尾**——结果是"越新写入的记忆越先被丢弃",正好反了。现在的规则见 §5,丢的是最旧的条目。

不过读写时机的不对称本身还在:**写入端不设限,只有下次启动读取时才截断。** 所以文件会一直长,直到某次启动突然告诉你丢了 20 条。想避免就定期看一眼启动时的警告。

## 7. 代码位置

| 文件 | 职责 |
|---|---|
| `src/memory.ts` | `loadMemory()` 分层加载 + 截断;`appendMemory()` 追加写入;路径解析 |
| `src/tools/remember.ts` | 工具定义。参数校验 + 强制打印,实际写入委托给 `appendMemory` |
| `src/prompt.ts` | 把 `LoadedMemory` 的各层拼进 system prompt,并声明优先级规则 |
| `src/index.ts` | 启动时调 `loadMemory`,打印加载了哪些层、是否被截断 |
| `src/config.ts` | `MEMORY_MAX_TOKENS`;`userConfigDir()` 决定 `~/.tcode/` 的位置 |

数据流:

```
启动
  └─ loadMemory(root, maxTokens)          读两层 + 按需截断
       └─ buildSystemPrompt({ memory })   拼进 system prompt,标明优先级
            └─ AgentDeps.systemPrompt     每一轮 llm.send() 都带着

运行中
  └─ remember({ scope, content })
       └─ appendMemory()                  追加到对应文件
       └─ context.log()                   强制打印给用户看
            (当前 session 的 system prompt 不会热更新,
             新记忆在下次启动时生效)
```

## 8. 明确不做的

- **不做语义检索 / 向量库。** 记忆是全量拼进 prompt 的静态文本。文件大到装不下时,现在的做法是粗暴截断——按相关性挑片段属于后续增强(spec §11)。
- **不做后台自动提炼。** agent 只在用户明确要求("记住…")或自己判断有持久价值时才调 `remember`。不做"每轮结束偷偷总结用户习惯"这种事:用户不知情的记忆写入,和不打印写入内容一样危险。
- **不做记忆的自动清理/去重。** 文件是用户可读可编辑的 Markdown,想删想改直接开编辑器。

## 9. 已知限制

- **当前 session 内新写的记忆不生效**,以及**最新的记忆最先被截断丢弃**——两条都是读写时机不对称导致的,详见 §6。后者是 spec 缺口,还没拍板怎么改。
- **没有冲突检测。** 追加两条互相矛盾的记忆,两条都会进 prompt,由模型自己判断。
- **`~/.tcode/AGENTS.md` 是全局的**,不区分机器/环境。多台机器之间不同步。
